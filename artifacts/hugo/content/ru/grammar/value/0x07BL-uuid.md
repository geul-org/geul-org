| Порядок | Поле (BIND) | FIELD | Ширина | Принимаемый формат (CODEC) | ENUM |

| 1 | `uuid` | #2 | простое значение, 8 WORD |  |  |

UUID — Value фиксированной ширины, хранящий 128-битное значение UUID по RFC 9562. Прямой код Value `0x07BL`, семейство BINARY. Payload — ровно 8 WORD (16 octet, 128 бит).

## Раскладка {#레이아웃}

```
TAG WORD          0x07B8 (0000 0111 1011 1000)  всего 9 WORD
Payload           8 WORD (128 бит)  UUID octet 0 → octet 15
```

## Интерпретация и действительность {#해석과-유효성}

- Канонические octet UUID по RFC 9562 с octet 0 по octet 15 группируются по два octet по порядку. Octet, идущий первым, — старшие 8 бит WORD. Field, version bit и variant bit UUID не переставляются и не кодируются заново.
- Строка hex-and-dash вида `8-4-4-4-12` — лишь форма ввода и вывода. Регистр и дефисы в Payload не попадают, сохраняются только 16 octet результата разбора.
- Этот Value UUID без потерь сохраняет 128-битный шаблон. При variant `10xx` по RFC 9562 version 1, 3, 4, 5, 6, 7 имеют стандартный layout, а version 8 — пользовательский формат UUID. Version 2 зарезервирована для DCE Security, и RFC не определяет её layout; version 0 не используется (unused), version 9–15 зарезервированы для будущих определений. Остальные variant тоже зарезервированы для совместимости или будущих определений.
- Nil UUID — особое значение, где все 128 бит равны нулю, Max UUID — все 128 бит равны единице. 128-битные шаблоны, включая зарезервированные и неиспользуемые version/variant, структурно не исключаются, а смысл такого шаблона и его совместимость определяются применяемым стандартом и внешним контекстом.
- Тождественность UUID определяется равенством 128-битных значений Payload. Равенство значений не гарантирует подлинности, владения, текущего существования, разрешимости или прав доступа к объекту.
- При хранении Microsoft COM GUID представление mixed-endian в памяти или при сериализации копировать как есть нельзя. Сначала его нужно преобразовать в 16 octet в каноническом порядке field/octet по RFC 9562.
- Если Payload не равен ровно 8 WORD, значение отвергается.

## Основание в стандартах {#표준-근거}

- [RFC 9562 — Universally Unique IDentifiers (UUIDs)](https://www.rfc-editor.org/rfc/rfc9562.html) определяет UUID как 16 octet (128 бит) и кодирует field начиная со старшего байта, так что в binary format field следуют в порядке big-endian. Variant находится в старших битах octet 8, version — в старших 4 битах octet 6, и этот формат сохраняет эти позиции как есть.
- Разделы 4.1–5.10 RFC 9562 различают variant, version 1–8, Nil, Max и зарезервированные диапазоны. RFC 9562 заменяет RFC 4122, поэтому действующая норма для этого формата — RFC 9562.
- ABNF hex-and-dash в RFC 9562 — текстовое представление, а оговорку о little-endian у COM GUID RFC указывает отдельно. GEUL помещает в Payload только канонические 16 octet UUID по RFC.
- GEUL TAG, прямая Length и обрамление 16-битными WORD — не часть RFC 9562, а правила, которые добавляет этот формат.

## Длина {#길이}

- Всего — ровно 9 WORD: TAG 1 WORD и Payload 8 WORD; используется прямая длина `LLLL=1000`. Расширяющего Length TAG, descriptor и padding нет.
- Если Payload не равен ровно 8 WORD, значение отвергается.

## Пример {#예시}

Тестовый вектор UUIDv7 из RFC 9562, Appendix A.6, `017f22e2-79b0-7cc3-98c4-dc0c0c07398f`:

```
07B8 017F 22E2 79B0 7CC3 98C4 DC0C 0C07 398F
```

- TAG `07B8`, Payload `017F 22E2 79B0 7CC3 98C4 DC0C 0C07 398F`.
