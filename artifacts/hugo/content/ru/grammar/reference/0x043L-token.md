## Поля (документ спецификации) {#필드-규격-문서}

Порядок FIELD в документе — это порядок полей Payload ([документ спецификации Codec](../codec-spec.md)).

| Порядок | Поле (BIND) | FIELD | Ширина | Принимаемый формат (CODEC) | ENUM |
|---|---|---|---|---|---|
| 1 | `code` | #2 | простое значение, 1 WORD |  | По одному на токен. Заполняется при публикации редакции 1 словаря |

TOKEN — это Reference, указывающий на одну запись словаря токенов GEUL. Словарь — это словарь BPE (Byte Pair Encoding), обученный на корейском и английском языках, а одна запись — это одна последовательность байтов. Если последовательно соединить последовательности байтов подряд идущих записей TOKEN, получатся байты исходного текста.

- Если словарь укладывается в 65 536 записей, используется только TOKEN-0. Если он становится больше, лишние записи размещаются в TOKEN-1. Даже если TOKEN-1 не используется, первый Codec называется TOKEN-0.
- Один токен записывается одной записью. Поскольку размер фиксирован и равен 2 WORD, k-я запись последовательности токенов находится на расстоянии 4k байтов от начала.

## Раскладка {#레이아웃}

```
TAG WORD          0x0431 (0000 0100 0011 0001)  TOKEN-0, всего 2 WORD
Payload WORD 1st (16 бит)           ID токена (uint16)

TAG WORD          0x0441 (0000 0100 0100 0001)  TOKEN-1, всего 2 WORD
Payload WORD 1st (16 бит)           ID токена − 65 536 (uint16)
```

- Код: прямые коды Reference `0x043L`·`0x044L` (раздел 2).
- Payload — это ID цели. Согласно [общей раскладке Reference](_index.md), это беззнаковое целое в big-endian, записанное минимальной шириной; поскольку ID цели всегда `0`~`65 535`, Payload всегда равен 1 WORD (`0` записывается как `0x0000`).
- Квантификации нет (квантификация читается только в системе 5Q).

## Интерпретация и действительность {#해석과-유효성}

- ID цели каждого Codec — это значение Payload. ID токена во всём словаре для TOKEN-0 равен ID цели, а для TOKEN-1 — 65 536 + ID цели.
- Каноническое представление токена — документ спецификации его Codec. Для каждого ID токена на FIELD `code` есть один [ENUM](../edge/0x0BDL-enum.md), и имя, связанное через [BIND](../edge/0x0A3L-bind.md) с этим Edge Id ENUM, — это последовательность байтов токена. Кодовое значение ENUM у TOKEN-1 — это значение Payload (ID токена − 65 536).
- Словарь — закрытый список. ID токена, для которого в документе спецификации нет ENUM, — invalid. Правило этого Codec важнее общего правила ENUM («необъявленное кодовое значение не является ошибкой»).
- **Байтовые токены:** ID токенов `0`~`255` — это по одному байту. ID токена совпадает со значением байта. Символ, которого нет в словаре, например символ вне корейского и английского, записывается байтовыми токенами своих байтов UTF-8. BIND-имя байтового токена — машинное имя `<0x00>`~`<0xFF>`, а его смысл задаёт это правило.
- **Прочие токены:** Последовательность байтов — корректный UTF-8, а BIND-имя — эта последовательность байтов как есть.
- **Декодирование:** Читайте последовательность записей TOKEN с начала и соединяйте последовательности байтов каждого токена. Символы UTF-8, составленные из подряд идущих байтовых токенов, тоже восстанавливаются этим соединением. Результат совпадает с текстом до кодирования вплоть до байта.
- **Кодирование:** Способ разбиения текста на последовательность токенов (правило разбиения и порядок слияния) зависит от редакции словаря. Один и тот же текст при другой редакции словаря может дать другую последовательность токенов. Результат декодирования от редакции не зависит.
- **Редакция:** Редакция словаря — это версия документа спецификации. Каждая редакция записывает хеши файла словаря и журнала обучения как [SOURCE](../edge/0x0C0L-source.md) в HEAD документа спецификации. Когда нужно указать редакцию, создавшую последовательность токенов, вместе с последовательностью сохраняется её версия ([CODEC-POINTER](0x042L-codec-pointer.md) (`0x00000000`, `0x00000430`, ID версии `n`)).
- **Только дополнение:** Новая редакция лишь дописывает ENUM и BIND в конец. Последовательность байтов однажды выданного ID токена не меняется, не удаляется и не переписывается. Поэтому любая редакция — надмножество предыдущей, а последовательность токенов, созданная более ранней редакцией, декодируется более поздней точно так же. Если словарь обучается заново с нуля и значения меняются, этот Codec не используется, а выдаётся новый номер Codec.
- Токен — это Reference, поэтому он может быть субъектом [BIND](../edge/0x0A3L-bind.md), [LABEL](../edge/0x0A4L-label.md) и [TRIPLE](../edge/0x0AAL-triple.md) (например, частота появления токена, язык).

## Длина {#길이}

- Всего — ровно 2 WORD: TAG 1 WORD и Payload 1 WORD; используется прямая длина `LLLL=0001`. Расширяющего Length TAG, расширяющего Codec TAG и TAG, специфичного для Codec, нет.
- Если Payload не равен ровно 1 WORD, запись отвергается.

## Пример {#예시}

Пока редакция 1 словаря не опубликована, у обычных токенов номеров ещё нет. У байтовых токенов номера определены правилом.

| Токен | ID токена | Полные WORD |
|---|---|---|
| байт `0xE3` | `227` | `0431 00E3` |
| байт `0x80` | `128` | `0431 0080` |

## Открытые проблемы {#열린-문제}

- Публикация редакции 1 словаря. После завершения обучения и проверки в документ спецификации вносятся ENUM и BIND.
- Формат размещения последовательности токенов в документе. Не решено, какое поле Edge или Value принимает последовательность записей TOKEN.
- Каноническая форма кодирования. Как записать в документе спецификации правило разбиения и порядок слияния, и фиксировать ли для одного текста единственную последовательность токенов.
- Интерпретация между редакциями. Когда читающая сторона встречает ID токена новее своей редакции, отбрасывать ли его как invalid или сохранять исходное значение и считать «неизвестным токеном».

## Исходный текст документа спецификации {#규격-문서-원문}

Документ спецификации `0x00000000/codecs/0x00000430/` публикуется вместе с редакцией 1 словаря. Пока он не опубликован. Вид следующий (для пояснения).

```
BODY
#1 DECLARE 0x0430
#2 FIELD #1 0x0001
#3 BIND #1 "TOKEN-0"
#4 BIND #2 "code"
#5 ENUM #2 0x0000
#6 BIND #5 "<0x00>"
…
```
